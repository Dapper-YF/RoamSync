## 最关键的判断

目前 AI 最不聪明的地方，是不能持续把**用户的目标、正在谈的对象、有效条件和对应证据**绑定在一起。它会调用工具，却可能回答另一日、另一处同名活动，或把“用户希望省力/符合忌口”说成“场所已经满足”。增加检索或 Agent 数量不会自动补上这些判断。

## 真实运行流程和边界

`assistant_service.send_message`先校验页面day/activity归属，再将它们作为只读指代传给`semantic_turn`。入口恢复本话题有效条件、固定相对日期收据；附着旅行时读取提交态。`saved_trip_reads.load_saved_trip_read`使用调用方数据库URL上的独立短REPEATABLE READ READ ONLY事务：Trip、偏好、日期、活动计数、最多100个活动/事项和关联打算时段来自同一MVCC快照，立即关闭连接。独立NullPool读通道每个应用事件循环/进程最多2连接，准入最多等5秒，异常/取消也关闭、dispose和释放准入；不从已被调用方占满的业务池借第二条连接。默认单进程预算为业务15+读取2，worker另计，没有增加业务池大小。`captured_at`是首条数据SELECT前的UTC时点。结束时通过DB标量复核Trip/偏好版本，已知更新要求重读；它不是对回答期间永不改变的保证。

selector和回答共享同一脱离ORM的保存状态。每个read_task用自己的原句投影范围；按所问日期/已验证selected优先读取，再给matched/returned/complete、歧义、Trip/偏好版本。普通列表与保存值直接由服务端渲染；原始理由明确传`original_rationale`，仍只信现有accepted revision的已验证记录。缺记录如实说无原始理由；回答阶段理由/notes与captured版本不匹配则`needs_retry`，不会误说记录不存在。入口捕获时的已知更新/繁忙沿原AssistantToolError API错误路径并提示重读，**并非所有入口都返回typed needs_retry**。

普通建议、地图、路线、天气、网页、图片继续既有工具。纯itinerary子任务的query/names/origin/destination/near_name不参与保存态读取，移除模型多填的这些参数，避免无用搜索参数阻断；**原句包含关系与其他工具参数/来源/行动授权检查保留**。复合任务保留独立结果和来源，一个路线失败不会抹掉已完成的日程读取。旧fallback保留原始限定，不再变成泛泛全程概览。

正式行动仍走既有候选→核验→Validator/Revision→明确采用。读取ID不增加写授权，不把UI选中永久存作偏好。B本版没有新增Agent、RAG、长期画像或第二套规划系统。

上下文仍有不同生命周期：本话题的城市/指代，不等于整趟预算/日期要求；明确个人偏好才有跨旅行保留依据；撤销/失效条件不能从旧历史复活。外部事实应保留实体、来源、查询时间与未知状态，不能写成用户偏好。B2已有范围/撤销处理，但同行主体与跨旅行范围仍未完整验收；本轮快照是一次读取的提交态，不是永久记忆。
