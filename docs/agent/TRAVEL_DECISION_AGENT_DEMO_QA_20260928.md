# Travel Decision Agent Demo Q&A

## 为什么这比普通大模型生成旅游攻略更像 Agent？

它读取正式行程和用户目标，再生成候选方案。系统会核对路线、时长和必去活动，最后等用户确认才改正式行程。

## Goal 和 Prompt 有什么区别？

Prompt 是这一次怎么说的原文。Goal 会被整理成“18 点前结束、少走路、尽量保留活动”等字段，Planner 和 Validator 都能据此工作。

## Decision Context 是什么？

它是这轮规划时相关的行程事实，例如当天安排、时间窗口和路线。它让模型拿到完成任务需要的信息，也给服务端校验提供依据。

## Memory 不是聊天历史吗？

这里展示的 Memory 是上次用户拒绝方案时留下的明确反馈，并能追溯到那份 Revision。第二轮从同一行程检索它，不依赖用户重复粘贴。

## Activity Semantics 为什么需要？

活动除了地点和时间，还有用户确认的含义，比如必去、能否跳过和最短停留时间。系统把这些当成候选方案必须遵守的条件。

## 为什么 LLM 不直接管理地点 ID？

模型只选择本轮提供的短引用。服务端再把它精确映射到正式活动或候选地点，防止模型编造或混淆数据库身份。

## 为什么还需要 Validator？

模型负责提出候选，Validator 负责确定性检查日期、时间、路线、活动语义和用户目标。模型的回答本身不能证明方案有效。

## Decision Ledger 为什么没有完成？

Ledger 还在 shadow 阶段，结果不会作为本阶段的演示依赖。当前只有经过核验的解释才会展示；Ledger MVP 和 Stage 2.2 都仍 OPEN。

## AI 为什么不能自动修改正式行程？

生成的只是待审候选，页面会保留“确认并应用”和“暂不采用”。只有用户主动确认后，服务端才重新校验并保存。
