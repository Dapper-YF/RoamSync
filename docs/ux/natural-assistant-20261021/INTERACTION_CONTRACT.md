# 自然助手交互契约 v0.1

状态：设计基线，供原型走查。以下“应当”是目标行为，不代表线上已经实现。配套审计见 AUDIT.md，落地映射见 IMPLEMENTATION_PLAN.md。

## 共同约定

- 对话、浏览、保存打算、采用日程、实际发生是不同动作。询问和兴趣不自动变成选择；已明确的模糊决定不因缺钟点而丢失。
- AI 主动研究、组合、给草案；已有明确规划请求无需再次询问“要不要开始”。只有会改变答案或阻塞安全执行的缺口才问用户。
- 用户可直接编辑已知时间，无需先说一句话；编辑的影响和来源仍保留。
- 只读页面背景不提供写权限。写入必须绑定当前用户动作、对象、范围和期望版本；候选仍经现有 Validator/Accept。
- 保存成功、仅收到消息、候选生成中、未保存必须用不同反馈。API 未确认前不能显示“已记下”。
- 日期统一 Asia/Shanghai；“明天”在表达时锚定绝对日期，刷新及午夜不顺延。

## C01 知识问答与未确定探索

触发：“成都人为什么喜欢喝茶？”、“先随便看看，不用安排”。直接回答，可按内容提供相关地点入口。不创建 Trip、打算或待确认方案。浏览/收藏不推断持续偏好。只有本轮实际引用的资料才显示为依据。

工具选择：稳定知识不固定全查；比较涉及位置时核实 POI；问现在如何到达时核实路线。工具失败保留可用部分，说明哪个结论未知。用户未要求持续监测时，不承诺后台提醒。

## C02 明确打算的自然保存

触发：当前用户明确表达“我明天下午去人民公园，几点再说”或“记下人民公园，日期没定”。只保存原话支持的地点、日期/时段及状态；不推断停留分钟、预约、行程顺序。

- 当前唯一可识别地点：保存后回复“已记下：10月22日下午去人民公园，具体时间未定”。提供“查看”“撤销”。不再要求用户先创建四日游。
- 同名地点未唯一核实：保留“人民公园（成都市，具体地点待核对）”这一文本打算；导航和精确排程前核实。不因身份待核实而丢失想法，也不自动选第一条 POI。
- 缺日期：保存为日期未定，不追问起止日期。缺城市且存在多个人民公园：允许保存原句并标注待明确，不宣称已解析成某个城市 POI。
- 假设、引用、别人的愿望、问句或“先别保存”不触发。重复消息 ID 不重复添加。重复表达同一项时由服务端关联原项，不能仅按名称合并不同出游。
- 若日期属于已有旅行但用户未明确归属，先保存独立打算，可提供“放入成都这趟旅行”；不因日期重合偷偷修改 Trip。
- “撤销”撤销本次写入或恢复前版本，不影响后来的修改；版本不一致时提示核对。取消打算不取消真实预约。

## C03 保存打算与会话的生命周期

打算是服务器确认保存的事项，可从“我的安排”找到，关联来源会话。关闭聊天、刷新、新对话不会删除；新对话也不会把旧事项作为当前目标自动带入。过期事项显示原日期，不每天重解释“明天”。

会话内有效条件仅影响适用话题，不代表跨会话个人偏好档案。正式旅行安排复用 Trip/ArrangementItem；会话打算归入旅行必须一次性关联并标记原项已转入，幂等且不双份生效。本轮原型只演示保留与隔离，不演示归入旅行事务。

## C04 AI 主动安排

触发：“帮我安排第二天，别太满”“把人民公园放进这一天”。在可见范围内读取已选、备选、留白、用户报告的预约和已有活动，使用现有 Planner 产生可校验候选。

默认不将备选强行排入，不侵入明确留白，不为路线更顺移走已订票活动。当前条件不足时提出一项关键澄清；能先给部分有用建议则先给建议。没有实时路线证据时不声称少赶路已核实，不将文本方案包装为通过 Validator 的正式候选。

用户应看到：安排内容、与原有内容的差异、保留了什么、影响哪一天、事实缺口。按钮命名为“采用11月3日的建议”等具体作用范围。采用前正式日程不改变。

## C05 继续商量、放弃与正式采用

- “继续商量”：保留当前候选 ID/版本和正式安排，聚焦输入，并展示讨论对象。不是 Reject。
- “放弃这份建议”：拒绝该候选；正式安排保留。
- “采用这份建议”：绑定当前可见候选 ID＋版本；保护规则仍在服务端检查。
- “就这样吧”遇到多份候选或未绑定候选时询问所指，不接受任意聊天段落。
- 精确单字段直接编辑可以走现有受保护服务；会影响其他活动的协调仍走候选。不能据“可撤销”跳过权限与版本检查。

## C06 页面与对话背景

界面展示“正在讨论：人民公园”或“成都这趟旅行 · 11月3日”，用户可移除/切换。后台传对象 ID；文案不作为身份。

| 用户动作 | 背景变化 | 权限 |
| --- | --- | --- |
| 查看地点详情或地图点选 | 更新浏览面板；保留既有对话焦点 | 只读 |
| 点击“讨论这里” | 显式替换讨论地点，保留返回页 | 只读 |
| 点击“调整这一天” | 绑定旅行、日期、可选活动；在输入上可见 | 当前消息仍需明确请求才生成候选 |
| 回到自由聊 | 清页面讨论焦点与写目标；历史保存内容保留 | 无旧旅行隐式写入 |
| 新对话 | 新 topic/session；当前条件和焦点清空，旧记录保留 | 不继承旧写权限 |

优先级：当前用户明确命名 > 明确选择的讨论对象 > 相关且未失效的对话指代。浏览地点与讨论对象不同且用户只说“这里/这个”，展示两项选择后再继续；任何修改/导航的歧义都不得静默选择。位置背景不等于 GPS。

## C07 附近推荐与路线

“附近吃什么”沿用可见的讨论地点，不要求 Trip、不把推荐加入安排。多个可能地点时先明确锚点。路线起点可以是用户选定地点，必须显示起终点与查询时间；未知物理位置时不宣称“你在这里”。

路线不可用时给出地点与重新查询入口，不补造距离/ETA。真实预约、支付、取消不由保存打算顺带触发。只有导航服务和授权可用时才显示持续导航状态。

## C08 修改、撤销与现实事实

“不去人民公园了”可取消明确的未执行打算；如已关联预约/执行或会影响其他正式活动，说明影响并走对应保护流程。用户报告“已订票”即应保护，但呈现为“你提供的预约”，不宣称订单核验。模型推荐不是预约事实；位置进入范围不是自动完成。

## C09 故障、版本、恢复

保存失败保留原输入与待保存内容，不乐观标已保存；重试复用幂等标识。采用遇版本冲突：保留新版本，标旧候选过期，保留修改要求，允许重新生成；禁止自动套旧结果。

刷新恢复已保存打算、可见范围和候选；后台返回的版本是依据。存储不可用的原型要显式提示仅本页保留。生产恢复需要服务器验证，不能以浏览器缓存作为写权限。

## C10 信息层级

聊天中仅在形成明确打算、关键条件改变、出现待采用差异时展示相关反馈，不为每句话生成概览。我的安排首先展示可回看的决定与当天内容；未定内容可保留。留白表示有意不安排，不显示待完成任务。要求/来源/时间锁定在需要核对时展开。没有活动的日期不出现“已经准备好了”的开场。

## 原型及未来产品验收表

| 编号 | 输入/操作 | 必须观察到 | 必须不存在 |
| --- | --- | --- | --- |
| T01 | 知识问答 | 有用回答 | 新建事项/Trip/采用弹窗 |
| T02 | 明确明天下午打算 | 绝对日期＋时段，查看/撤销 | 必填开始时间/时长 |
| T03 | 同一消息重试 | 同一记录 | 重复保存 |
| T04 | 保存失败再重试 | 未保存提示，原输入可恢复 | 提前成功文案 |
| T05 | 保存后刷新与新对话 | 原记录仍在；新焦点为空 | 丢记录/旧目标自动写入 |
| T06 | 请 AI 排第二天 | 第二天候选；留白/预约保留 | 修改其他天/填满留白 |
| T07 | 继续商量 | 同一候选保留 | 清预览/调用 Reject |
| T08 | 采用前发生新版本 | 冲突提示/候选过期 | 覆盖新版本 |
| T09 | 浏览另一地点后说“这里” | 显式选择讨论对象 | 偷偷换锚点 |
| T10 | 天气/路线查询失败 | 明确未知及可继续的选择 | 编造雨情/ETA/保证 |
| T11 | 只咨询或收藏 | 可继续探索 | 偏好/计划自动新增 |
| T12 | 已决定但无具体时间 | 持久化可回看，仍可请 AI 安排 | 自动填写钟点 |
| T13 | 直接修改已知时间 | 次级编辑可用，保留版本保护 | 强制转聊天 |
| T14 | 用户撤销或改日期 | 指向原项；原日期不随午夜变化 | 误删预约/改其他项 |

T01–T10 的合成原型覆盖情况与实际执行记录见 evidence/verification.json。T11–T14 的完整产品验收及真实模型/数据库/外部服务验证不得由原型测试结果替代。
