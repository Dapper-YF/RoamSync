# 最小必要工程改动

状态：基于交互契约和可运行原型确定的实施建议，尚未修改产品代码或数据库。不是整套架构重构计划。实际实施必须从当前脏工作区继续核对，不能覆盖前轮功能。

## 原型验证带来的决定

1. 默认入口可以从填时间改为“请 AI 建议怎么安排”；已知时间的直接编辑保留在次级展开中。原型已走通两种路径，无需更换路由、框架或 Planner。
2. 一份候选只有一个明确状态：未采用、已过期或已采用。继续商量只改变讨论焦点；不能借 Reject 实现。
3. 讨论日期和地点必须可见。现有消息协议已经有 selected_day_id / selected_activity_id，先补调用链，不再设计万能 Context 服务。
4. 保存打算是一个小而真实的新增能力。现有 TripArrangementItem 必须属于 Trip；有效条件槽位不等于事项；AssistantSession.messages 是对话记录，trip_id 还带级联删除关系。不能为了“零迁移”把独立事项伪装成活动、偏好或聊天成功提示。

## 建议分三批实施

| 批次 | 精确改动 | 主要文件/接缝 | 完成条件 |
| --- | --- | --- | --- |
| M1：修复交互断点 | 将继续商量与拒绝分开；助手头部显示旅行/日期/活动；显式退出旅行；传递已有 selected 参数；切换旅行清除失效日期和候选指针 | web/src/product/AssistantDecisions.tsx、TravelAssistant.tsx、journeys/journeyApi.ts、JourneyPage.tsx、domain/types.ts；消息/流请求共享类型 | 继续商量不发拒绝请求；选第三天只规划第三天；回自由聊后无旧写目标；刷新恢复须校验对象归属 |
| M2：调整页面默认操作 | ArrangementExtras 的地点选择增加“请 AI 建议”；合并当天事项、活动和候选的主视图；时间编辑次级展开；要求/来源按需查看；空日程移除“准备好了”文案 | JourneyPage.tsx、ArrangementExtras.tsx、TravelAssistant.css；复用现有 arrangementApi | 一天一个主视图；留白不成为待补任务；直接编辑仍可用；AI 候选不提前改变已确认活动 |
| M3：补独立打算保存 | 在现有统一语义决策中提取当前用户明确打算；服务端进行来源/时间/范围校验、持久化、幂等和撤销；我的安排读同一份数据 | assistant_capabilities.py、assistant_turn.py、assistant_memory.py 的来源校验接缝；独立小模块与最小迁移；前端保存反馈/列表 | 无 Trip、无钟点可保存；服务确认后才报成功；新对话可找到；重试不重复；撤销有版本；不进入正式活动写入器 |

M1 可先独立交付；M2 依赖 M1；M3 可以在两者稳定后接入。M2 在 M3 完成前不能出现“未归属旅行的打算已经保存”的产品承诺。每批单独验证，不捆绑发布。

## M1 的具体协议边界

- JourneyAssistantContext / TravelAssistantContext 增加选定 day/activity 的 ID 与只读显示名。日期显示名不能替代 ID。服务端现有 selected 参数负责归属验证。
- send 与 stream 使用同一组 selected 字段，不只修非流式入口。
- 显式“调整这一天”绑定日期；浏览日签不偷偷改变正在修改的候选。两者不一致时显示候选原日期，不能把它放在另一天标题下冒充该天建议。
- “继续商量”保留服务端 pending_action / pending revision；前端只聚焦输入及其绑定对象。“放弃这份建议”才发送 accept=false。
- 用户随后要求调整候选时，正式旧安排不变；新候选替代关系和版本由现有候选服务维护。不得只修按钮却让下一条消息隐式丢弃旧候选。
- 退出旅行清当前作用范围；旧会话仍保留。“新对话”沿用现有创建空会话的逻辑，不用 reset 删除历史。

## M3 的最小数据和接口建议

以下是提案，不是现有接口。选择一个独立的轻量记录实体（例如 SavedIntention），一张表即可；不增加新 Agent、图状态机、事件总线或通用记忆平台。增加它的依据是 C02/C03 的独立生命周期和 A04 的实际模型限制。

最小字段：id、source_session_id（可空、删除会话时置空）、source_message_id、source_text、captured_at、timezone、place_text、city_text、place_id（可空）、identity_status、intended_date（可空）、time_period（可空）、status、version、linked_arrangement_item_id（可空）、created_at / updated_at。只保存本次打算所需数据，不复制整段历史。来源重复约束至少覆盖消息＋该消息内事项索引；语义相似本身不作为唯一键。

建议复用消息接口完成自然保存，在结构化响应中返回 saved_intentions / intention_write_result。查询和显式撤销通过受限接口处理：读取已保存事项、按 ID＋expected_version 撤销、以后按原项 ID 转入旅行。不新增模型任意 SQL 或任意写权限。失败必须有 machine-readable 结果，但错误枚举名称在正式实施时按现有契约流程确定。

现有本地应用没有在 AssistantSession 模型/路由中体现用户所有权字段，不能直接发明 /me 接口或开放“枚举所有会话”。M3 实施先沿用当前应用的可访问范围，明确记录列表的访问约束；若需公网多用户，所有权须单独补齐后才开放跨会话查询。本轮不借此扩展为认证架构工程。浏览器只缓存 ID/展示状态，不能作为保存事实或写权限来源。

保存事务：检查消息来源为当前用户 → 绑定原陈述时间 → 提取模糊事项 → 校验非引用/假设且无拒绝保存 → 持久化并返回 ID/版本 → UI 显示已记下。无法核实地点时保存文本与待核对标记；不得自动填精确 POI。复用统一决策的结构化提取，拒绝扩展正则大全或每轮额外调用一个意图模型。

转入旅行事务（可后续）：校验目标 Trip/版本、创建/关联既有 ArrangementItem、标原项已转入；同事务且幂等。选中地点依然不是精确 Activity；实际排时走既有 PlanningRun → Validator → Revision → Accept。

若独立表的所有权、转入、来源约束尚未落地，可先发布 M1/M2；不得用 localStorage 原型顶替 M3 服务端验收。
