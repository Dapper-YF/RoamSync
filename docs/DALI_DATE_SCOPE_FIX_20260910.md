# 大理三天行程的日期范围修复

## 复现记录

旅行 `5b05edbe-7693-409e-a2ca-aee275b22ea3` 的日期为 2026-09-10 至 2026-09-12。
失败任务 `044d607c-b763-4ffb-ae44-4f52d6d90cdb` 的请求为：

> 请调整大理三天两晚（2026-09-10 至 2026-09-12）的行程，确保包含苍洱大道、龙龛码头、最美S湾等著名景点。

保存的意图为 `modify_day`，`target_day_ids` 只有 9 月 10 日。原规则只有在出现“完整行程”等重规划词时才识别全程日期范围，否则取第一个日期作为修改目标。同时，模型输入的 `trip_days` 仍提供三天，与只允许第一天的 schema / 输出校验冲突。最后显示的 `planner selected an unknown place or date` 也没有区分地点与日期错误。

## 修改

- 将与已保存旅行起止时间一致、由“至/到/横线”等连接的完整日期范围识别为旅行背景；独立的“第二天”或具体日期仍作为局部修改目标。
- 单独提及两个不相连的日期不会被当成全程授权，咨询问题也不会变成修改请求。
- 模型的 `allowed_dates`、`trip_days` 与动态 schema 使用同一组日期。
- 范围外活动仅作为背景，由后端保留；不再允许模型把这些活动移入目标日期。纠错输入也过滤范围外活动。
- 日期越界和未知地点分别返回具体中文错误，保留一次模型纠错及后端最终校验。
- 实际验证还发现别名引用过严：“最美S湾 → 磻溪S湾”有网页支持，但模型同时给了无关来源下标，原来的 `all` 判断会丢弃全部对应。现按与景点证据相同的规则保留有效引用；全部无效或多个不同对应时仍拒绝自动选择。

## 验证

- 后端全量：226 passed；2 项现有 Starlette 弃用警告。
- 回归覆盖原始请求、含 ISO 日期范围的助手改写、中文日期范围，以及相同旅行背景下明确只改第二天/9 月 11 日。
- 验证局部规划输入与 schema 日期一致、保留范围外活动、日期和地点错误可区分。
- API 与 worker 已重新构建并启动，`/health/ready` 返回 ready。
- 实际重试任务：`f85e4be7-44c5-40ea-b304-98b1f8902714`。请求与原失败任务一致，保留页面默认选中的第一天。初始解析为 `create_plan`，无单日限制。
- 别名问题复现后，以 `docs/evidence/dali-research-debug.json` 保存的真实网页资料与研究输出重放同一任务，地图和后续规划仍调用真实服务，避免重复检索带来的输入变化。

重放后，三天日期和三个指定地点通过模型输出校验。任务进入实际路线校验，并在一次自动修正后因 `route_unavailable` 停止：2026-09-12，双廊古镇 → 理想邦，高德未返回公共交通路线。旅行偏好仍为步行、公交，未擅自启用自驾。完整错误与意图解析见 `docs/evidence/dali-date-scope-retry.json`。

日期范围与别名修复已验证；本次并未生成可采用的完整候选，也未修改正式活动。剩余限制是实际交通可达性，不能把地图未返回公交路线解释成地点不存在或用户日期表述有误。
