# 统一旅行助手：对话创建、改期与复用（2026-09-09）

本阶段沿用一个「旅程总管」入口和组件，在旅行首页与行程内使用同一套持久化对话、工具调度和候选确认流程。

## 用户可以做什么

| 场景 | 示例 | 实际行为 |
| --- | --- | --- |
| 首页创建 | 明年元旦去成都两天，两个人4000元，以美食为主 | 补齐具体日期和目的地，展示创建预览；确认后创建旅行，携带对话进入工作台并生成首版候选 |
| 当前旅行改期 | 把这趟旅行改到2027年2月1日至2日 | 展示改期预览，确认后按天平移原有活动，旅行状态按新日期计算 |
| 参考旧旅行 | 参考这趟旅行，明年3月再去一次，不覆盖原旅行 | 创建独立旅行，继承适用偏好；同城同天数时保留参考布局，再生成候选；旧消费、完成记录和对话留在原旅行 |
| 解释与建议 | 目前怎么走？给两个让第二天更丰富的建议，先不要修改 | 读取正式行程作答，不生成替换方案 |
| 连续追问 | 就按第二个建议，只改第二天，保留午餐和晚餐 | 用上一轮正式回答补全调整请求，交给现有候选、校验与确认流程 |

Enter 发送、Shift+Enter 换行，并保留中文输入法组词保护。手动创建入口仍然可用。

## 保存与数据边界

- 工具仅限回答、创建、改期、复用、询问行程、调整行程六种。模型返回结构化提议，应用代码核对城市、日期、预算、来源旅行后执行。
- 目的地通过现有地图城市搜索校验。缺少具体日期或总预算时继续问，不自行指定出行日期。
- 创建旅行、保存偏好、绑定对话及排队规划任务在同一次事务中完成。排队失败会整体回滚，保留原操作预览供重试。
- 消息 ID 和操作 ID 支持幂等处理；操作预览保存旅行版本、偏好版本和活动指纹，源旅行修改后旧预览不能继续提交。
- 改期保留日期页 ID、活动 ID 及内容，按第几天平移；过时的待处理规划和候选失效，不能再覆盖新日期。
- 复用创建新的旅行 ID，不复制实际消费与执行历史；参考活动恢复为待游玩并解除旧锁定。旧旅行保留对话记录，新旅行承接讨论上下文。
- 创建旅行后，具体活动仍须在候选方案中确认保存，正式工作台随后读取已保存数据。

## 本轮验收中修复的问题

1. 新增前端请求漏了 JSON Content-Type，真实服务返回422；已修正全部对话接口并补充传输测试。
2. 调度层与回答层各自给出不同的建议，导致“第二个建议”含义不一致；调度层现在只确认接收需求，最终回答只展示一次，后续上下文使用实际回答。
3. “保留原有两个用餐点”被旧实体解析当成地点名称；现在按所选日期、真实地点类别和用餐时间解析餐饮活动组，不将另一日餐厅误纳入本次调整。
4. 补充真实任务状态到对话上下文，发现“没有候选却声称准备就绪”时要求调度纠正，仍不一致则明确报错，不展示虚假的成功消息。
5. 日期解析排除“第一天保持不变”等保留边界，避免与真正要修改的第二天冲突；餐厅名称前的“原有的午餐”等描述也能解析到真实活动。
6. API容器重建后地址可能变化，Web代理改为重新解析Docker服务地址，避免旧地址缓存导致502。

## 当前范围

一次工具操作支持1至31天。缩短旅行时如果多出的日期仍有活动，会要求先处理或选择复用，避免静默删除。跨城市或改变天数的复用先继承适用偏好，再生成新布局。跨旅行对话是上下文继承，不是全局永久偏好记忆；模型每次读取最近对话和规划结果。订票、付款、自动删除及后台主动监测不在本阶段范围内。
