# 保留旅行设置被识别为活动的修复

## 实际记录

任务 `b65cfcb2-815e-43bb-b9d9-5ce83aca2296` 的规划请求，在用户要求包含三个大理景点的原话后补了“保留原有日期、目的地与预算不变”。

`_PROTECT_PATTERNS` 提取“保留”后的全部文本，按顿号等连接词拆分，再统一匹配活动，产生了 `activity_not_found:原有日期`、`activity_not_found:目的地` 和 `activity_not_found:预算不变` 三个错误。这些错误来自规则解析器，不是用户缺少必要信息。

## 修改

- 识别完整的日期、目的地、预算、交通方式等设置引用，并允许“原有/已保存/保持/不变”等修饰。这些设置继续使用当前旅行保存的值，不作为需要定位的活动。
- 按完整引用匹配，不能因为真实景点名称包含“日期”等字就忽略它。
- 保留具体活动、餐厅、未知景点的既有定位与澄清逻辑。
- “保留预算不变”不再生成 `adjust_budget` 操作，也不误设为不得超过当前活动总费用；空行程的活动总费用为零，不应把新规划预算压成零。
- 同样过滤语义解析结果中误提取的设置引用，避免另一路径重现相同无效追问。

## 验证

- 全部后端测试：231 passed，2 项既有 Starlette 弃用警告。
- API / worker 已重新构建并启动。
- 实际完整请求经 `/planning-intent/resolve` 返回 `requires_clarification=false`、空澄清问题、`create_plan`，无单日限制和未解析活动。
- 从原任务的研究检查点恢复，保留原请求与既有检索资料，不伪造用户补充回答。

任务恢复后的结果另见 `docs/evidence/trip-setting-clarification-recovery.json`。

恢复后已越过错误澄清，执行真实模型规划与地图路线校验。最终因 `route_unavailable` 停止，没有生成可采用的候选，也没有保存正式活动。此次设置解析问题已解除，交通可达性是仍需处理的独立限制。
