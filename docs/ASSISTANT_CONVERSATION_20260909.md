# 旅行助手问答与安排理由（2026-09-09）

用户指出：“现在的旅行行程是怎样的，你建议我怎么走这一趟？”属于询问，助手却生成了一份替换方案。助手必须能够解释、建议、比较与规划，不能把所有输入都变成重规划。

## 原因

- `run_type=replan` 被用作未知意图的兜底，页面上下文替代了用户的明确要求。
- 语义层已有 `answer` 策略，但创建任务接口拒绝该分支，LangGraph 也只有规划和澄清流程，没有实际回答节点。
- 模型生成的逐项 `reason` 没有展示，方案总理由又被固定模板覆盖。
- 等待确认的候选会禁用主输入框，用户无法继续问“为什么这样安排”。

## 行为调整

| 用户输入 | 助手行为 | 是否创建候选 |
| --- | --- | --- |
| 现在行程怎样、建议怎么走 | 介绍正式安排、分析节奏与路线、给出有依据的可选建议 | 否 |
| 为什么这样安排、预算花在哪里 | 回答问题；涉及未采用候选时区分候选与正式安排 | 否 |
| 景点比较、推荐、旅行准备、寒暄 | 在旅行上下文内回答，缺少事实时明确说明 | 否 |
| 请修改第二天、重新规划、希望丰富整趟旅行 | 生成候选，展示理由、费用与影响，确认后才应用 | 是 |
| 无法理解的输入 | 明确提示或请求澄清，不默认生成整趟行程 | 否 |

## 实现

- 新增持久化 `answered` 状态和 `response_text`，通过迁移 `20260909_0018` 增加字段及状态约束。旧任务与旧候选保持兼容。
- 在同一个任务入口与助手中接通独立的只读回答节点；该节点不调用候选生成、保存或接受逻辑。
- 回答读取正式活动、已查询路线、预算、偏好、有限历史对话及最近候选说明。未确认候选必须与正式行程区分。
- 去掉未知输入默认重新规划；规则先识别询问语气，模糊输入交给已有语义解析器。明确的变更请求仍进入预览，现有校验与确认边界不变。
- 候选必须返回针对本次要求的解释和逐项选择理由。展示的总体变更说明由后端对比实际前后地点生成，避免模型叙述的新增/保留数量与方案不一致；逐项显示模型提供的地点/时间选择理由。模型原始总体解释保留在候选快照中供核查。
- 预计费用与相较原行程的变化由后端计算，包含未出现在候选中的锁定/进行中/已完成活动，排除跳过活动。总体解释禁止自行输出金额、交通分钟数和公里数，避免解释数字与候选实际数据矛盾。
- 前端支持文字回答、简单强调和历史回读；已有待确认方案或待补充问题不再锁住主输入框，仍可继续提问。正在生成时避免重复提交。
- 保留 Enter 发送、Shift+Enter 换行与中文输入法保护。

## 验证与范围

- 后端 167 项测试通过，含截图原话及多类问题分流、显式修改、问答不创建 revision、不修改正式行程与版本、解释结构和金额校验。
- 前端 44 项测试通过，含等待确认时提问、文字回答恢复、逐项理由展示与发送快捷键。
- 12 项浏览器回归通过，含问答响应展示且无应用按钮、正式数据不变。
- 类型检查、lint 和生产构建通过。API、worker、Web 已重建并更新本地服务。
- 在独立副本进行真实模型验证，用户正式行程未修改。精简记录见 [assistant-conversation-20260909.json](evidence/assistant-conversation-20260909.json)。

实测期间发现了额外的回答质量问题：旧备注被混入正式时间表、历史天气被说成未来预报、模型自行合计费用出错。已从问答输入中移除旧备注、屏蔽已过去行程的天气预报数据，并加入日期判断、步行上限核对及费用由后端计算的约束。自然语言建议仍可能存在主观取舍或事实表述误差；本次验证不能代表所有开放问题都已实现确定性事实验收。
