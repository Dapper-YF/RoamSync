## Authoritative contracts

The Pydantic definitions in `backend/app/schemas.py` are authoritative:

- `PlanningIntentParseRequest`: normalized non-blank message plus optional UI
  context.
- `SemanticIntentDraft`, `GroundedIntent`, and `IntentPolicyDecision`: strict
  semantic, entity-binding, and workflow-policy layers carried by
  `PlanningIntentResolution`.
- `PlanningIntent` and `PlanningRequest`: backward-compatible planning fields
  consumed by the current Planner prompt.
- `PlanningRunCreate`: `initial_plan` or `replan` plus a required, non-blank
  request of at most 4,000 characters.
- Formal `Activity` responses carry the user-authored `importance` decision
  semantic (`low`, `normal`, `high`, or `must_do`). It is supplied to the
  Planner as a soft preference; deterministic sacrifice constraints are added
  only with the corresponding Phase 2 validator slice.
- `CandidatePlanSnapshot`: at most 100 unique candidate activities and at most
  200 uniquely positioned route legs.
- `PlanningClarificationInterrupt`: `kind`, one or more questions, and `run_id`.
- `PlanningApprovalInterrupt`: `kind`, `run_id`, and `revision_id`.
- `PlanningRunDecision`: only `clarify`, `accept`, or `reject`; clarification
  requires a non-blank answer.
- `PlanValidationResult`: hard errors and non-blocking warnings.

Unknown fields are forbidden on intent and interrupt inputs. The semantic parser
emits no operation mode or database identifiers. Its output must pass
deterministic grounding and the policy gate before the graph may plan. The legacy
four-value `PlanningIntent` vocabulary remains only as a compatibility field;
workflow routing uses the structured operation list and policy decision.

## State machine

```text
queued
  -> researching
  -> awaiting_clarification -> researching       (at most two answers)
  -> planning
  -> validating
       -> planning                               (one correction only)
       -> awaiting_confirmation
  -> goal_check
       -> planning                               (at most one hard-goal repair)
       -> awaiting_confirmation
  -> accepted | rejected | failed
```

The implemented graph nodes are:

```text
START -> resolve_intent -> clarify? -> plan -> validate
      -> review? -> plan -> validate -> goal_check
      -> goal_repair? -> plan -> validate -> goal_check -> persist -> approval
      -> accept | reject -> END
```

`cancelled` is a reserved persisted status; Agent v1 exposes no cancellation
transition. A second validation failure terminates the run with
`planner_constraints_unsatisfied` and creates no pending revision. A valid
candidate that still misses an explicit deterministic hard Planning Goal is
given one structured repair attempt; a second miss terminates with
`goal_constraints_unsatisfied`. Soft goals are observations only and never
block a revision.

Human clarification and final approval use explicit interrupts. Side effects
before an interrupt must be idempotent. Resuming with the wrong decision kind or
resuming a terminal run is rejected.

## Candidate evidence and hard validation

Every candidate activity must reference a trip-owned `PlaceCandidate` and its
trip-owned `SourceRecord`. Costs are copied from backend records, never trusted
from the model. Every adjacent pair in the complete candidate day, including
formal locked, active, or completed activities that remain in place, must have a
`CandidateRouteLeg`.

Acceptance re-runs validation while locking the revision, run, and trip. At
minimum, these conditions block acceptance:

- unknown or cross-trip place/source/replacement IDs;
- date outside the trip or daily time window;
- overlapping activities or insufficient route time;
- changed locked, active, or completed activities;
- omitted or changed activities outside the grounded day/activity scope;
- new activities outside a grounded target day;
- increased estimated cost when the grounded constraint forbids an increase;
- daily or total budget violation when a Trip budget limit is configured;
- missing or structurally inconsistent route evidence;
- formal trip version different from `base_trip_version`;
- revision or run no longer pending confirmation.

Rejecting a candidate changes only the run and revision decision records. It
must not change formal activities, routes, or the trip version.

## Provider and tool policy

### Draft provider

- Production configuration is injected through `Settings`; secrets never enter
  graph state, prompts, responses, or database snapshots.
- The Responses API is called with JSON Schema output and `store=false`.
- Provider timeout and SDK retry count are bounded by
  `PLANNER_TIMEOUT_SECONDS` and `PLANNER_MAX_RETRIES`. The outer planning
  execution also has an `AGENT_RUN_TIMEOUT_SECONDS` wall-clock deadline; an
  expiry marks the run failed as `planning_run_timeout` and releases its worker.
- Agent workers claim up to `AGENT_WORKER_CONCURRENCY` independent runs at once
  (default 2), so one slow provider call cannot block the whole queue.
- The model may choose only supplied place IDs and trip dates. Backend code
  resolves costs, sources, replacement IDs, and routes.
- Candidate names, descriptions, tags, and user text are untrusted data, not
  instructions.

### Semantic intent provider

- High-confidence dates and UI references are resolved by deterministic code.
- Requests left as legacy `unknown` use the configured DeepSeek/OpenAI-compatible
  Responses endpoint with the `SemanticIntentDraft` JSON Schema.
- The provider extracts semantic operations and mentions only. Backend grounding
  owns IDs, completeness, risk, confirmation, and workflow routing.

### Map provider

- Production requires `AMAP_REST_KEY`.
- `ALLOW_MAP_ESTIMATES=true` is permitted only for tests and explicit local
  development. It is not a silent production fallback.
- Provider rejection, credentials failure, quota exhaustion, network failure,
  and missing configuration remain visible as stable failures.

### Deferred tools

Weather, Web Search, OCR/multimodal import, and community-content extraction are
outside Agent v1. They require separate input/output, source, timeout, retry,
cache, privacy, and failure contracts before becoming graph nodes.

## Decision Ledger validation responsibility (2026-09-27)
