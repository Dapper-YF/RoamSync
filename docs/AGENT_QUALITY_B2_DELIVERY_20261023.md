## 结论与验收边界

目前最不聪明的地方仍是：组件知道调用什么，却不能持续对同一个用户目标负责，尤其会把“已记住用户的限制”当成“推荐场所已满足限制”的证据。用户条件、地点身份、未知事实和行动范围在组件交接时会脱节；最后一段流畅的建议容易超出实际证据。

## 代码实际运行流程

Assistant receipt 固定相对日期锚点 → 恢复服务端有效条件 → 一次 CapabilityDecision 提出意图、条件、子任务或创建/规划 draft → 服务端检查当前原句/肯定授权/目标/版本 → 各 read task 带自身参数执行。路线的 POI 查询只负责路线端点，独立地址仍执行；失败保留兄弟结果。Companion 接收已批准的信息需要，direct 假设不能被下一层重新升为天气查询。最终统一汇总来源与可见编号。

正式行动沿用原有 prepare_action → pending confirmation → create/queue → Graph → Validator → Revision → Accept。PreparedPlanningIntent 绑定原文、Trip、页面 selected IDs、Trip 与偏好双版本。Worker 恢复 marker 中相同 draft，重新核实当前实体/范围/政策，不再调用语义提取。API 澄清领取时先持久化 literal answers/receipts；Graph 只用最后一条回答补尚缺的目标日期，原请求/verb/已定日期不变。旧 checkpoint 兼容单独验证，不将拼接回答当新授权。

条件仍是会话 JSON 中的有界状态（设计意图，生命周期正确性未整体验收）：topic/trip/destination/personal v2 范围；换城市清目的地条件，换旅行只保留有明确个人来源的偏好；撤销保存为 unknown/withdrawn，不从旧历史重新赋值。外部事实不写入个人偏好。没有长期记忆库、新 Agent、RAG 或第二个规划系统。

## 三项优先问题与本轮取舍

1. **同一任务在组件之间失去原目标与授权。** 复合读取漏目标、确认后重解释、澄清扩展请求会使用户无法连续委托。本轮实施同决策交接、逐任务参数/来源，以及原请求不变的 prepared 恢复；读取与合成恢复闭环有证据，真实规划采用闭环仍失败。
2. **有效条件没有真正更新。** 用户改日期、撤销预算后，正文与保存状态可能互相矛盾。本轮实施有来源的规范值、极性/范围检查、撤销投影及直接复述；公开连续对话证明这几项改善，同行信息和长期范围仍未通过完整验收。
3. **推荐理由越过证据。** 无场所动线、座椅、菜单或营业资料仍给“满足15分钟”“雨再大都不影响”的保证。这是当前最高的旅游判断风险。本轮保留其失败、补来源聚合与缺口审查，但没有完成可靠的事实充分性判断；不能把前两项工程收益算成此项已解决。下一轮优先做可验证地点身份与对应事实支持，避免继续扩充禁词。

优先实施前两项是因为它们在现有接口内可保留原意、建立可复现状态与恢复闭环；第三项需要地点身份、证据粒度与答案判断共同改变。此取舍不降低第三项的发布阻断级别，也不把严格拒绝误称为用户成功完成任务。
