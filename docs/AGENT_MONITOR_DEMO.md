# Agent 运行监控演示

本页把旅行总管的真实请求、Agent 阶段、tool、验证与用户决定放在同一屏幕中。左侧复用现有旅行总管，右侧以中文时间线和带时间的事件流展示执行过程。只展示结构化结果与观测事件。

## 入口与启动

- 当前已验证入口：`http://127.0.0.1:3000/dev/agent-monitor`。
- 指定旅行：`/dev/agent-monitor?trip=<旅行编号>`。
- 指定历史运行：`/dev/agent-monitor?trip=<旅行编号>&run=<运行编号>`。
- 独立监控：加 `split=0`；默认与旅行总管左右并排。
- 后端保持现有 Compose 运行方式。在项目根目录运行 `npm --prefix web run dev` 可启动前端开发入口。
- 当前 `3000` 端口仍是原有容器页面。本轮完整 Web 镜像构建尝试被既有的 16 项测试失败阻断；随后工作树存在并行组件 / 测试修改，最后一次 Web 回归仍有 3 项失败；本轮没有绕过镜像测试门禁。

首次打开时，左侧读取真实旅行列表，选择现有旅行；右侧显示该旅行的真实运行。没有运行的旅行会显示空状态。未提供旅行编号时，从实际旅行列表选择第一趟旅行，不使用虚构默认数据。

## 实际链路与数据来源

请求先进入 `assistant_routes.message_endpoint → assistant_service.send_message → travel_goal_router`。

普通咨询进入独立对话 Agent：理解目标 → 绑定对话对象 → 确定信息需求 → 按需读取上下文 / 知识 → 生成回答 → 提取交互结果 → 检查规划授权边界 → 准备持久化 → 保存并返回。调用真实知识检索和回答模型时，另外显示 tool 节点。使用资料直接回答或安全降级时，模型 tool 不会被伪造出来。

明确规划请求沿用既有链路：旅行 tool 选择 → 创建 `PlanningRun` → worker / LangGraph → 意图解析与按需研究 → 候选方案 → 路线补充 / 确定性验证 → 目标检查 → `PlanRevision` → 用户接受或拒绝。

| 展示阶段 | 真实组件 / 数据 |
| --- | --- |
| 用户请求 | `PlanningRun.user_request`；通过会话中精确的 `run_id` 关联原消息 |
| 意图理解 | `planning_intent_service`、运行的 `intent_resolution`、观测事件 |
| 目标提取 | `planning_goals`、阶段事件、检查点或候选版本保存的目标 |
| 上下文构建 | 当次保存的 `planning_context` / `before_snapshot`，不拿当前行程补写历史 |
| 目的地研究 | `destination_research`、外部事实、实际研究分支记录 |
| 地点匹配 | 已保存的候选地点、地图解析事件；无需研究时显示跳过 |
| 规划与候选方案 | `openai_planner`、结构化候选活动和 `decision_summary` |
| 路线事实补充 | `candidate_route_service` 与保存的路线分段；可能使用缓存 |
| 确定性验证 | 验证结果、真实错误代码和 `goal_satisfaction`，由程序执行 |
| 候选行程版本 | `PlanRevision` 的原行程、建议行程、差异与版本信息 |
| 用户决策 | 运行 / 候选版本的实际接受、拒绝、补充信息状态与反馈 |
| 普通对话的实时阶段 | `dialogue_observation` 对现有节点和实际 tool 的阶段观测 |

## 观测与同步约定

规划监控继续读取 `PlanningRun.progress.events`、候选版本和必要的持久化检查点。普通对话新增有界、按 `(session_id, message_id)` 隔离的进程内观测，记录阶段名称、开始 / 结束状态、真实时刻和耗时；容量最多 64 个请求，30 分钟过期，每个请求最多 80 条事件。

观测包装保留原返回值与原异常，故障不会改变路由、模型选择、重试、验证或行程权限。没有数据库迁移。普通对话观测不保存消息内容、完整上下文、完整请求响应、隐藏提示、模型内部推理或凭据。

只读接口：

- `GET /api/v1/agent-monitor/runs?trip_id=...`
- `GET /api/v1/agent-monitor/runs/{run_id}`
- `GET /api/v1/agent-monitor/sessions/{session_id}/messages/{message_id}`

前端使用同源 `BroadcastChannel` 立即获知请求发送，再约每 2 秒轮询实际阶段。规划记录严格绑定本条对话返回的运行编号；不会用一条不相关的较新运行替代它，也不会让旧请求的迟到响应覆盖新请求。普通对话没有创建规划运行时，不展示旧的规划记录。

演示时在左侧发送请求，可以保证对话和监控同源。不同端口或不同域名之间无法共享前端通知。

## 推荐演示旅行与输入

已验证旅行：`00000000-0000-4000-8000-000000000002`，显示名为 `Goal-Aware Demo · 杭州从容一日游`。实际日期为 2026 年 10 月 20 日，具有既有正式活动和锁定活动。这趟旅行没有 19:00 演出的记录，不能把示例约束当作真实事实展示。

先展示普通对话：

```text
西湖有哪些历史文化特色？
```

本轮实际观察到读取资料并直接形成回答，没有模型 tool。再展示需要模型的建议请求：

```text
我想在杭州找一些适合摄影的活动，请给我两个有文化特色的建议。
```

本轮实际观察到知识检索 tool、回答模型 tool 的执行中与完成状态，模型阶段约 76.88 秒，没有新建规划运行。

规划链路的已验证输入：

```text
请把2026年10月20日行程中最后一站河坊街·南宋御街的游览时长调整为30分钟，其余活动和时间保持不变。仅修改已有活动，不新增、不替换地点。
```

实际运行 `a5ede415-6165-4636-a2b9-97998a374d13` 使用 `glm-5.3-flash`，约 23.7 秒后创建候选版本并等待用户确认。研究与地点匹配实际跳过，路线补充与验证完成。天气 tool 失败后按原有业务规则降级，不等于整个运行失败。该运行随后在数据库中记录为已接受，正式版本从 1 变为 2；本轮工具没有主动发起接受请求。该记录适合回放；再次提出相同请求是否产生修改取决于当前正式行程。

真实失败样本 `117886ad-1355-47e2-9394-425b57d6de77`：轻松下午与减少步行的请求触发目的地研究，因 `planner_research_unavailable` 失败。保留它用于说明错误可观测性，不把它呈现为成功规划。

## 五分钟讲解与实时操作

1. 打开指定旅行的监控页，点击“全屏”和“演示模式”。默认左右并排，自动跟随阶段；开发者 JSON 隐藏。
2. 左侧发送文化咨询，说明 Agent 先分流并读取需要的资料，咨询不自动改正式行程。
3. 发送建议请求，观察回答模型 tool 的黄色执行状态和实际耗时。
4. 发送明确规划请求，讲解目标与上下文；点击阶段可暂停自动跟随并查看结构化证据，勾选“自动跟随阶段”恢复。
5. 展示路线事实和程序验证，再展示原行程 / 建议行程 / 差异。
6. 说明候选方案等待用户决定；在左侧点击“确认并应用”才接受。“暂不采用”走原有拒绝流程。用户决策阶段和正式版本会持续更新。

不要为讲解而强行让每次请求走全部节点；跳过、不适用、未记录和失败都是实际结果的一部分。

## 历史回放与网络容错

在“历史运行”中选择上述成功运行，页面自动关闭“跟随最新运行”，显示“历史回放”和“历史事件流”。也可直接打开：

```text
/dev/agent-monitor?trip=00000000-0000-4000-8000-000000000002&run=a5ede415-6165-4636-a2b9-97998a374d13
```

该运行的 11 个阶段和 19 条事件在后端重建 / 重启、浏览器重载后仍能读取。若模型、搜索或地图不可用，保留失败记录，切换到此真实历史运行讲解即可。重新勾选“跟随最新运行”返回实时监控。

页面刷新后若左侧没有自动展开候选方案，可展开旅行总管的“对话与方案记录”，选择对应运行，再查看方案。右侧回放不会替用户接受或拒绝历史候选版本。

## 当前限制

- 普通对话的逐阶段时刻和耗时是进程内观测，服务重启后消失。既有会话仍持久化普通对话的 `runtime_trace`，但当前“历史运行”选择器只回放规划运行。
- 进程内观测适用于当前单 API 进程部署；多 API 进程下应改用共享观测存储，不能宣称支持分布式实时 Trace。
- 轮询可能一次读到多个已完成的短节点，不用动画延时重演它们。
- 旧运行缺失的阶段耗时、tool 历史或结构化原因保持不可用。运行中的“已执行”由真实起始时刻计算，不是最终测量耗时。
- 路线缓存读取不代表真实发起了逐段 HTTP 请求；当前研究 / 验证阶段也可能覆盖多个内部操作。没有 MCP 调用记录，不展示虚构 MCP。
- Web 修改前有 16 项失败；并行修改后的最后一次回归为 3 项既有失败，后端对等基线有 14 项失败。本轮监控专项通过，不能据此宣称项目全量测试通过或整体演示已冻结。
