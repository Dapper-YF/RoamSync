## 5 分钟演示顺序

1. **产品定位（20 秒）**：RoamSync 不是一次性生成攻略，而是让地图、日程、预算和智能调整共享同一份旅行状态。
2. **完整旅行（50 秒）**：打开杭州两日一夜计划，切换两天，展示酒店位置、活动时间线、预约备注和真实高德路线。
3. **可操作规划（50 秒）**：选择活动、编辑时间或备注，拖动排序，切换步行/公交/驾车路线，强调修改写入 PostgreSQL。
4. **真实地点（40 秒）**：打开候选地点，通过高德搜索杭州地点并加入日程，展示来源记录与预算同步。
5. **Goal-Aware AI 规划（90 秒）**：打开顶部 AI 助手，先用一句话明确旅行日期、要调整的日期、希望少走路并在 18:00 前结束、尽量保留现有活动；只讨论时补上“先分析，不要修改”。确认要执行后，观察 Agent 解析目标、读取正式行程、生成候选、校验约束并等待审批。只有点击“确认并应用”才修改正式行程。右上角“打开监控台”会在新标签页打开当前旅行的实时 Agent 控制台。
6. **旅中执行（50 秒）**：打开“旅中模式”，开始旅行，依次展示已到达、开始活动、完成活动和下一站推进。刷新后执行状态仍会恢复。
7. **产品全景（40 秒）**：打开旅行总览，展示住宿、城际交通、天气、预约清单和全场景预算。明确酒店、票务和天气是产品预览。
8. **技术收束（30 秒）**：刷新页面证明数据保留；说明 React Web、FastAPI、PostgreSQL、LangGraph、GLM-5.3-Flash 和高德组成当前规划链路。

## 建议汇报页

1. 用户痛点：攻略、地图、预算和临时变化相互割裂。
2. 产品方案：同一份旅行状态驱动规划、执行、预算与调整。
3. Web 工作台：地图主导 + 按日时间线。
4. 真实能力：城市/POI、最短路径、数据库持久化。
5. Agent 安全闭环：意图解析 → 候选生成 → 硬约束校验 → 人工确认 → 事务落库。
6. 杭州案例：两日一夜完整演示。
7. 产品路线图：天气动态重排、酒店/票务供应商、旅中 Android、GPS 与消费闭环。

## 现场异常预案

- AI 响应慢：继续展示已保存的正式杭州行程，并说明模型调用在后台 Worker 中，不阻塞手工规划。
- 高德服务波动：已持久化的路线仍可展示；不要现场重置数据。
- 南京续接演示无需重置数据库；请使用确认预览创建一趟独立的南京旅行。
- 不要展示或口述 `.env` 中的任何 API Key。

## 展示边界

- 真实：旅行、活动、预算、偏好、地图 POI、路线、Agent 候选与接受后的数据库写入。
- 真实：旅行执行状态、活动实际时间、暂停/恢复和执行事件历史。
- 产品预览：酒店房型与价格、火车票、天气。数据已集中在 Preview 结构中，界面明确标注“未创建真实订单”或“展示预测”。

## 南京对话续接与 Agent 监控台演示

本段接在用户已表达“国庆想去南京玩三四天、一个人怕无聊”，并问过南京城市、老街巷之后。前置聊天若发生在 ChatGPT 等其他窗口，不会自动写入 RoamSync 的 AssistantSession；演示时要在 RoamSync 的旅程总管里重述必要背景，下面第一条输入已包含这些信息。

保持 Compose API 在 `127.0.0.1:8000` 运行，另开 PowerShell 执行 `npm --prefix web run dev`。创建旅行前从 `http://127.0.0.1:5173/trips` 打开“旅程总管”，点击其标题栏的 **“打开监控台”**，新标签页会打开不带旅行筛选的 `/dev/agent-monitor`；并排模式左侧也能显示创建前对话。创建旅行后，工作台右上角和旅程总管标题栏的入口都会打开当前旅行的监控台 `/dev/agent-monitor?trip=<当前旅行编号>`。保持工作台和监控台同源，从旅程总管发送消息时，监控台显示这条对话的真实阶段；新建旅行后筛选跟随当前旅行。

### 1. 探索南京，展示目标分流、按需检索和知识边界

**用户输入**

> 接着我们刚才关于国庆去南京、一个人玩三四天的讨论：我对历史街巷和本地小吃感兴趣，想轻松一点。请先只聊思路，不要创建旅行或修改任何行程。如果你目前没有关于南京的可靠资料来源，请直接告诉我，不要猜。

**预期流程与回复**

- 请求进入普通 Companion 对话链，不创建 `PlanningRun`、`PlanRevision` 或正式行程变更。
- 系统按需尝试知识检索。当前审阅语料集中在杭州；南京主题很可能显示“当前小型知识库不覆盖这个目的地或主题”或“没有检索到相关资料”。按页面实际返回说明，不补充无来源的景点事实。
- 可以口播：“监控台显示 Agent 识别为旅行探索，只读检索所需知识；资料不覆盖时它会说明边界。本轮没有规划运行，也没有改动正式行程。”

> 提醒：原始对话中那段关于老门东、颐和路等地点的描述可作为前情素材，不代表当前 RoamSync 已核验这些南京事实。不要用它作为实时来源或已验证回答演示。

### 2. 明确创建新旅行，展示追问上下文、操作预览和用户授权

**用户输入**

> 好，那请现在帮我创建一趟南京旅行：2026 年 10 月 2 日出发、10 月 5 日返程，一个人，总预算不超过 3000 元，住新街口附近。偏好历史、人文、街巷和本地小吃，节奏轻松，每天 9 点左右出门、21 点前结束，连续步行尽量不超过 45 分钟。老门东、颐和路和中山陵是我感兴趣的地点；请把它们作为需求交给规划流程，但不要把未核实的开放或预约情况当成事实。先给我看创建预览，等我确认。

**AI 与界面应走的流程**

1. 这次请求明确要求新建旅行，才进入 Planning/tool 路径；它不应把上一步的“只聊思路”当成改行程授权。
2. 城市标准化和日期、预算检查通过后，助手给出“确认创建旅行”预览。按现有服务响应，回复类似：

   > 请核对：南京市，2026-10-02 至 2026-10-05，共 4 天，总预算 3000 元，每日预算 750 元。确认后执行。

3. 暂停在预览卡片上，讲解目的地、日期、预算及偏好摘要。先点“暂不执行”可以展示取消路径；重新发起后点“确认创建”，才创建正式旅行记录并启动首版候选行程任务。
4. 新旅行被打开后，监控台随工作台切换到南京旅行，展示真实 PlanningRun 的状态、阶段、研究/地点匹配、模型候选、路线事实、验证、目标满足情况和人工确认。某阶段如果真实显示“已跳过”“不可用”或“失败”，按实际结果解说；不保证每次请求都经过所有节点。
5. 候选版本等待用户决定时，指出正式行程尚未应用。点击“确认并应用”后再展示实际用户决策、行程版本和已保存结果。

### 3. 拒绝并按反馈重规划，展示持久反馈和变更范围

在首版候选卡片中选择“暂不采用”，原因选“走路太多”，补充“中山陵保留，下午安排紧凑些，预算不要增加”。之后明确发出第二个操作请求：

> 请按我刚才的反馈重新规划南京行程，保留中山陵，减少连续步行并控制总预算不增加。先给候选方案，不要直接保存。

监控台应出现新的重规划运行；如系统实际取回拒绝反馈，可展示它与原候选版本的关联。新方案仍需经过约束校验并等待用户确认。讲清“拒绝旧候选不会改变正式行程；新候选也要重新审批”。如果当前候选没有可靠南京地点或研究来源，安全失败并保留旧正式状态是有效演示结果，不要临时添加虚构来源。

### 汇报口播（约 45 秒）

“我们从用户担心一个人旅行无聊开始。先让助手讨论南京想法，同时明确这还不是创建行程的授权。监控台能看到普通对话实际走过的理解、上下文/知识检索和回答阶段；它也会显示资料库目前覆盖不到南京，避免把没有证据的内容包装成核验结果。用户明确要创建后，系统先把南京、日期和预算放进操作预览；只有用户确认才创建旅行并运行首版规划。候选方案经过路线、时间和预算检查后仍要人工确认。若用户拒绝并说明走路太多，后续规划可以读取这条真实反馈，再生成新的待审候选。整个过程中，普通咨询、候选方案和正式行程写入有清楚的权限边界。”

### 实际演示边界

- 对话的普通 Companion 阶段来自当前 API 进程的实时观测；规划历史来自真实运行记录。监控页会把“未创建规划运行”和“没有经过的规划阶段”如实显示。
- 当前审阅知识资料主要覆盖杭州；不要把南京文化问答描述为已有来源支撑的已验证能力。
- 城市/地点查询、实时天气/搜索及模型都受现场配置和网络状态影响。调用失败时展示真实失败阶段或使用已记录的杭州成功运行回放；不要口播虚构耗时、来源数量或成功率。
- 本项目有新建旅行预览、候选规划与用户审批；不代表已实现南京景点预约、门票或酒店订单。
